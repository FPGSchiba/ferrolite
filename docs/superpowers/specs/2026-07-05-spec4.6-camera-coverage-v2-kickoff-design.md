## 1. One-paragraph summary

Spec 4.6 closes out v1. It has two halves. The **camera-coverage** half is structurally
unusual: the real fix for a missing camera (a new decoder or a new color matrix) lives
**upstream in `rawler`** — which this project pins from crates.io and **never forks**
(v1 map §2 / Spec 4 map §3.3) — so it cannot land in this repo. This branch therefore
ships the one genuinely in-repo, user-facing coverage improvement (**surface when a RAW
decoded without a camera color matrix, so the user knows the colors are approximate**),
and writes the rest of the coverage work up as a **prioritized recommendations + upstream
workflow** document. The second half is the **v1 finale**: author the **v2 architecture-map
kickoff prompt** — a brainstorm-kickoff artifact that hands a future agent the job of
decomposing a professional-grade v2, carrying v1's licensing tiers and cross-cutting
contracts forward.

The branch ships exactly **three deliverables**: one small code feature (D-A) and two
documents (D-B, D-C).

## 3. Deliverable A — user-visible camera color-profile coverage status (code)

### 3.1 Problem

Today, when a RAW's camera has no usable color matrix, `ferrolite-decode` builds
`ColorProfile::srgb_fallback()` (`is_fallback = true`) and logs a one-line `eprintln!`
(`ferrolite-decode/src/color.rs:58`). The colors are approximate (sRGB primaries assumed),
but **the user is never told** — the flag is dropped after it is used to build the
camera→working matrix. This is the concrete, in-repo camera-coverage gap we can fix.

### 3.2 The data is already present — no plumbing

`is_fallback` flows all the way to the app already:

```
decode_full(path) → RawDecoded.color_profile           (ferrolite-decode/src/raw.rs:112)
  → AppEvent::FullDecoded { color_profile, … }          (ferrolite-app/src/viewer/load.rs:114)
  → apply_full_decoded()                                 (ferrolite-app/src/app.rs:766)
  → ViewerState.color_profile                            (ferrolite-app/src/viewer/mod.rs:182)
```

The chip needs no new decode product and no new event; it reads existing `ViewerState`.

### 3.3 Correctness: derive status from three inputs, not from `is_fallback` alone

A naive `color_profile.is_fallback` check is **wrong** in two ways:

1. `ViewerState.color_profile` is **seeded to the sRGB fallback** at open and only becomes
   the real profile once the tier-2 full decode arrives (`ferrolite-app/src/viewer/mod.rs:182`
   doc: "sRGB fallback until full decode"). Before that, `is_fallback == true` for *every*
   image — showing the warning during the preview phase would be a false alarm.
2. **Standard (JPEG/PNG) images** have no camera-matrix concept; `is_fallback` is
   meaningless for them and must never produce a warning.

So the status is a pure function of `(kind, full_ready, is_fallback)`. Introduce a small
**pure, egui-free helper** in `ferrolite-app` (e.g. `develop/coverage.rs`), unit-tested:

```rust
/// User-facing camera color-profile coverage state for the open image.
pub enum CoverageStatus {
    /// Not a RAW (Standard raster) — no camera matrix concept. Render nothing.
    NotApplicable,
    /// RAW, full decode not yet complete — the profile is still the seed
    /// fallback and is not authoritative. Render nothing.
    Pending,
    /// RAW decoded WITH a real camera matrix.
    Calibrated,
    /// RAW decoded but no usable matrix — sRGB fallback in effect (the warning).
    Fallback,
}

pub fn camera_coverage(kind: FileKind, full_ready: bool, is_fallback: bool) -> CoverageStatus {
    match kind {
        FileKind::Standard => CoverageStatus::NotApplicable,
        FileKind::Raw if !full_ready => CoverageStatus::Pending,
        FileKind::Raw if is_fallback => CoverageStatus::Fallback,
        FileKind::Raw => CoverageStatus::Calibrated,
    }
}
```

**Implementation note (verify during the plan):** `full_ready` (`ferrolite-app/src/app.rs:939`)
is the tier-2 decode-complete signal. Confirm it is set at or after `color_profile` is
populated by `apply_full_decoded` (`app.rs:766`); if there is any ordering gap where
`full_ready == true` but `color_profile` is still the seed, gate `Calibrated`/`Fallback`
on whichever signal guarantees the real profile is in place. The truth-table tests below
are written against the *semantics* above, independent of the field chosen.

### 3.4 UI — a camera-info row at the top of the Develop adjustment panel

In `ferrolite-app/src/develop/adjustment_panel.rs`, add a compact camera-info row at the
top of the panel (above the existing sections):

- **Camera name:** `"{make} {model}"` from `ViewerState.meta` (loaded async by
  `develop::meta_read::spawn_meta_read`; `Option`), rendered in `theme::TEXT_DIM`. Before
  `meta` resolves, fall back to the file name (or render the row without a name) — never
  block on it.
- **`Fallback`** → an inline **warning chip**: a styled label in `theme::SEMANTIC_RED`
  (e.g. `"⚠ approximate color"`), with
  `.on_hover_text("No color profile for this camera — colors are approximate (sRGB \
  fallback). Consider contributing a sample upstream to rawler.")`. There are no custom
  badge/pill widgets in the design system, so this reuses styled `RichText` labels + the
  existing `on_hover_text` tooltip idiom already used in this codebase.
- **`Calibrated`** → quiet: show only the camera name (no chip), to avoid clutter. (A
  subtle affirmative may be added if the author wants it at visual-test time; default is
  nothing.)
- **`Pending` / `NotApplicable`** → the chip is absent (and for `NotApplicable`, the row
  may still show the camera name if `meta` provided one, e.g. for a JPEG with EXIF).

**Per-control-reset rule (CLAUDE.md) does NOT apply.** This is a **read-only status
indicator**, not an adjustable control — there is nothing to reset. This is called out
explicitly so the reset-affordance checklist does not flag it as a gap.

**Threading (CLAUDE.md rule 1):** rendering is O(1) label work on the UI thread; no decode,
I/O, or CPU work is triggered. Honored trivially.

### 3.5 Tests

- **Unit (pure):** `camera_coverage` truth table — all four states:
  `Standard → NotApplicable`; `Raw & !full_ready → Pending`; `Raw & full_ready & is_fallback
  → Fallback`; `Raw & full_ready & !is_fallback → Calibrated`.
- The egui presentation layer stays thin and is verified by the **author's hands-on visual
  test** (per CLAUDE.md), not by an automated UI test.
- Existing `ferrolite-decode` fallback tests (`color.rs`) remain the guard that
  `is_fallback` is set correctly at the source; unchanged.

### 3.6 Out of scope for D-A

Building a full metadata/info panel (only the camera-info row is added); a Library-grid
badge for fallback images; changing the fallback matrix itself; any new decode product.

## 4. Deliverable B — camera-coverage audit + recommendations (doc)

A single committed markdown document (`docs/` — proposed
`docs/camera-coverage.md`) with three parts:

### 4.1 Coverage today (as-built reference)

- RAW decode is **fully delegated to `rawler` 0.7.2** (crates.io, pinned; ~500+ models);
  there are **no in-repo camera tables or per-camera overrides**.
- The extension gate is `RAW_EXTS` in `ferrolite-catalog/src/scan.rs` (26 RAW extensions).
- The color path: `ColorProfile::from_color_matrix` prefers D65, else any present
  illuminant, else `srgb_fallback()` (logged); consumed by
  `ferrolite_color::camera_to_working` (`ferrolite-decode/src/color.rs`,
  `ferrolite-color/src/camera.rs`).
- Test fixtures: one CC0 RAW (`fixtures/raw/sample.rw2`, Panasonic).

### 4.2 Deferred hardening backlog (each with a disposition)

The pieces we deliberately did **not** build on this branch, written up so they are not
lost — each tagged **cheap-now / upstream / defer-to-v2**:

- **Camera-coverage audit tool** *(defer-to-v2 / dev-tooling)* — a dev command/test that
  walks a folder of RAWs and classifies each as *decoded-with-matrix* /
  *decoded-fallback* / *unsupported-by-rawler*, producing the exact artifact used to file
  upstream contributions.
- **`RAW_EXTS` ↔ rawler consistency test** *(cheap-now-or-v2)* — a test guarding that the
  classified-as-RAW extension set stays honest as coverage grows (don't accept extensions
  rawler can't decode; document ones it can).
- **Structured fallback logging** *(cheap follow-up)* — replace the raw `eprintln!` no-matrix
  warning with structured `tracing` (once-per-model, includes make/model) for field
  diagnosability.

### 4.3 Upstream contribution workflow + cadence

- **Never fork rawler.** To add a camera: contribute a RAW sample and/or color matrix
  **upstream** to rawler; coverage lands here only when upstream tags a release and this
  project bumps the pin (note the MSRV/`rusqlite`/`--all-features` constraints recorded in
  prior memory before any bump).
- **Cadence (proposed default):** bump `rawler` opportunistically when an upstream release
  adds a model this project's users have requested — not on a fixed schedule. *(Open for
  the author to adjust — §7.)*

### 4.4 Camera-family prioritization (proposed default — open)

Proposed priority for sample/matrix contributions and coverage attention: recent
**Canon CR3**, **Nikon Z (NEF)**, **Sony (ARW)**, **Fujifilm (RAF)** bodies, then whatever
an audit run flags as fallback/unsupported. *(Open for the author to adjust — §7.)*

## 5. Deliverable C — the v2 architecture-map kickoff prompt (the finale, doc)

A committed prompt document (proposed
`docs/superpowers/specs/2026-07-05-v2-kickoff-prompt.md`) that instructs a **future agent**
to run a brainstorm producing a **v2 architecture map**, mirroring the v1 map's structure
and discipline. It is a **brainstorm-kickoff artifact — explicitly not a v2 design.**

### 5.1 Structure the prompt hands off (mirrors the v1 map)

The prompt directs the v2 map to contain: one-paragraph summary → **settled decisions** →
**workspace crate decomposition** (carrying the **engine-transferable vs photo-domain**
tiers forward) → **spec → plan decomposition** into phases (as v1 was decomposed into
Specs 1–4) → the **five cross-cutting interface contracts** (carried forward, extended only
if justified) → references. It also instructs the agent to run the superpowers cycle
(brainstorming → writing-plans → implementation), one phase per branch, exactly as Spec 4
was kicked off.

### 5.2 Proposed v2 feature inventory (the prompt *proposes*, the v2 brainstorm *decides*)

- **Classical track (Lightroom/RawTherapee-class):** local adjustments / masking (brush,
  linear + radial gradients — the Develop toolbar's **Heal/Mask/Grad placeholders**),
  healing / clone / spot removal, edit **presets + copy-paste/sync across images**, **batch
  edits**, **advanced tone** (parametric curves, color-grading wheels), **noise reduction**,
  **print / soft-proofing**, **tethered capture**, and a **plugin / extensibility** story.
- **AI/ML track (explicit, its own decomposable area):** **AI denoise**, **subject/sky
  auto-masking**, **generative heal / remove**. The prompt **flags the open tier questions**
  for the v2 brainstorm rather than answering them: inference runtime (e.g. ONNX Runtime /
  `candle` / `wgpu` compute), **model-weight distribution + licensing**, and keeping the
  **engine-transferable crates free of copyleft deps *and* model weights** (the AI runtime
  and weights live in the photo/app tier or a new dedicated tier the v2 map defines).

### 5.3 Carried-forward discipline the prompt mandates

- The **licensing-tier invariant** (engine crates copyleft-free; new heavy/AI/C toolchains
  get a **build-gating decision** — feature flag / vendoring — so CI and contributors
  without them still build green, exactly as Spec 4.2's libjxl and 4.4's Lensfun did).
- The **cross-cutting contracts** as the seams; **catalog-is-a-cache**; **jobs are
  universal**; **per-control reset** for every new adjustable control; **build-once GPU
  pipelines**; and **green-gate-then-author-visual-test** before finishing any phase.
- The AI-era caveat that image quality was *secondary* in v1 is **revisited** by v2 (a
  professional-grade successor may promote quality to a primary goal) — the prompt names
  this as a settled-decision the v2 brainstorm must explicitly confirm or overturn.
